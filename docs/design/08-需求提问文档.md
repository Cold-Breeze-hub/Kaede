## 2. 问题

### A. 定位与边界

**A1【必答】第一版是「只给你自己用的工具」，还是「会拿给别人用的软件」？**  
定稿 §1 写「个人自用、单机、不公开分发」，但文档里同时出现了「检查更新」按钮（定稿 §2.4）、NSIS 安装包、便携版、规则导入/分享、`aria-label` 与无障碍清单。前者可以砍掉一大半工程投入（打包签名、自动更新、错误文案表、图标集、a11y）；后者这些都得留。

- 默认：按「自用，但做得体面」推进 —— 保留安装包与图标集，**不做**自动更新服务与云端。
- 答：会发给几个朋友

**A2【必答】「补老番为主」与新番向功能的关系？**  
定稿 §1 说「以补老番为主、有计划性；新番较少，一般仍走 B 站」，但功能版图里有新番时间表、排行榜 podium、标签广场趋势值、游戏的「即将发售」。

- 默认：第一版这些页面**界面照做**（定稿 §4 视觉与 §2 结构已定），数据可以用内置/演示，不保证实时。
- 答：必须真能拉到新番数据

**A3【影响】「只取日本作品」是硬边界吗？**  
定稿 §1 明确排除欧美 IP 与中文网文。但百科刮削（Bangumi / AniList）和源站搜索会带回范围外作品。

- 默认：入库时按 IP 白名单过滤，搜到范围外不展示。
- 请答：不拦，只是不主动收

**A4【必答】内置规则包 vs「不内置任何源站地址」**  
我在 `01` §6.5 写了「不内置任何资源站地址；规则由用户导入」，但 `05`/`04` 又写了「内置默认规则包，首次启动自动加载」——这两句有张力：内置规则包就等于内置了源站地址。

- 答：第一版内置几条（我默认 3 条），可以从 Kazumi 社区规则直接导入。

**A5【可后补】平台**：默认只做 Windows、不为 macOS 抽象（P6）。要不要留 macOS 的口子？

答：可以留macos的口子

我默认写的是 G1→G5 逐级：**主闭环可点通 → 真实源播完一集 → 读到卷章能续 → 整季下载能断点续传 → 全站走查过红线**（`01` §9 / `00` §5）。

### G. 分工与协作（你刚问的那个）

**G1【必答】按页面分，还是按层分？**

| 方案                       | 怎么分                                                                                                                                                          | 优点                                  | 代价 / 风险                                                                                  |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------- | ---------------------------------------------------------------------------------------- |
| **A · 按层**（`06` 现状）      | A 独占 `src/` 全部页面与动效；B 独占 `core/` 全部能力；`shared/` 共管                                                                                                           | 领域层只有一个 owner，不会出现两套播放/下载/DB；契约边界干净 | 「这个页面谁管」没答案；M1 的 A 是瓶颈（全部页面 2 周），M2–M4 的 B 是瓶颈（所有真实能力）                                   |
| **B · 按页面**（你提的）         | 两人各领一组页面，**端到端**负责该页的 UI + 所需领域能力                                                                                                                            | 页面归属清晰、负载天然均衡、界面还原有人兜底              | 播放/下载/资源/DB/契约是**跨页共用**的：两人都写 `player` 就会各写一套；必须事先把 `shared/` 契约冻结到字段级，且每个共用能力指定唯一 owner |
| **C · 页面认领 + 能力独占**（我推荐） | 页面按人分（每人是所认领页面的唯一负责人，含该页验收）；同时 `core/` 下按能力域切给两人各自独占，例如 A 管 `library/reader/search/music`，B 管 `source/player/proxy/download/resource/disk`；`shared/` 共管、契约先行 | 「这个页面谁管」和「这个能力谁改」**都有唯一答案**；负载能均衡   | 需要一张「页面 × 能力」归属表（我可以按你选的分组立刻出），且共用组件（卡片/进度条/弹层）仍要指定一人统一维护，不许各自复制                         |

- 答：C，每人都能写全栈

## 3. 直接回答你的问题：文档里现在还写不清楚的地方

不绕弯，我通读后认为有 8 处：

## 6. Kazumi 是怎么做的（回答 D5 / D1 / §3-7）

你说「kazumi 是怎么处理的？可以学习一下」，查证如下（Kazumi 官网规则文档 + 第三方拆解）：

### 6.1 元数据刮削：走 Bangumi 开放 API，不需要 API key

| 能力        | Bangumi 端点                       | 说明                                                                      |
| --------- | -------------------------------- | ----------------------------------------------------------------------- |
| **新番时间表** | `GET /calendar`                  | 每日放送，返回近 100 KB 结构化数据，含节目/评分/封面 —— 这就是 A2「必须真能拉到新番数据」的答案，**可行**         |

| 作品详情      | `GET /v0/subjects/{id}`          | 标题、简介、封面、评分、放送信息、tags、infobox                                           |

- **鉴权**：公开数据**无需鉴权**，只需在请求头带 `User-Agent`（声明应用名与联系方式）。
- **限流**：建议 **≥ 0.5 s 一请求**，本地缓存（Kazumi 与各类客户端都这么做）。
- 需要 OAuth 的只有「我的收藏/进度」相关（`/v0/me` 等），**我们不做**（定稿：无账号、单机）。

### 6.2 规则：社区 JSON + XPath/JSONPath，官方不内置任何源

Kazumi 的规则就是一个 JSON「网站说明书」，示例（仓库自带 `AGE.json` 形态）：

```json
{
  "api": "1", "type": "anime", "name": "AGE", "version": "1.5",
  "baseURL": "https://example.com/",
  "searchURL": "https://example.com/search?query=@keyword",
  "searchList": "//div/div/section/div/div/div/div",
  "searchName": "//div/div/h5/a",
  "searchResult": "//div/div/h5/a",
  "chapterRoads": "//div/div/section/div/div/div/div/div",
  "chapterResult": "//ul/li/a"
}
```

- 规则只负责两件事：**搜索**（返回作品名 + 来源标识/地址）与**选集**（返回播放线路 + 剧集）。
