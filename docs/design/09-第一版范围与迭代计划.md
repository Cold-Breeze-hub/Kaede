## 1. 第一版是什么（一句话）

> **一个能真搜索、真播放、真下载的动漫追番工具：界面完整覆盖五个分区，但只有动漫分区的能力是真的。**

对应你的原话：至少跑通一个分区（动漫）的完整链路；视频播放器和下载功能必须有；阅读器、音乐播放器不要求；得是一个能用的、真实可行的完整软件，只是其他功能暂时没做。

两条硬边界：

- **界面层**：全站 **1:1 还原，以原型为下限基线——不允许比原型差**（结构、密度、文案、动效一致），**允许更优的改进**，但每处偏离必须过定稿 §8 四问并登记到审查清单，不允许「随手改」（`08` §7 C-1 已确认）。
- **能力层**：只有动漫分区端到端是真的；游戏 / 漫画 / 小说 / 音乐分区**有界面、无真能力**——按 **`08` §7 C-6 乙**：全页面保留，所有未实现动作统一给**明确的「功能未开放」提示**，并在定稿 §9 登记 v1 豁免（不视为假交互红线）。

### 2.4 动漫分区完整闭环（v1 的核心，必须真）

端到端链路，任何一环断掉 v1 就不成立：

```
搜作品（Bangumi）→ 入库 → 详情页（真元数据 + 剧集）
  → 点集 → 并发搜多源 →【跨源自动拼出一整季】→ 选源播放
  → 本地代理 + hls.js 起播 → 进度写回 → 退出/杀进程 → 续播回到上次秒数
  → 播放器内切源 + 失败自动回落 → 切集 / 自动连播
  → 退出播放页 → miniplayer 小窗 或 纯音频（作品信息显示在条上）
```

| 能力 | 要求 | 依据 |
| --- | --- | --- |
| 跨源拼集 | 同一季的每一集可来自不同站，自动选最优源 | D3 |
| 播放在播放器内切源 | 主源 404 后 2 秒内切次源并提示 | FR-PLY-05 |
| 进度与续播 | 倍速/音量记忆，重开回到上次秒数，杀进程不丢 | FR-PLY-09 |
| 键盘与进度条 | 空格/←→/↑↓/N/Esc；点 70% 跳到 70% | FR-PLY-04/06 |
| **miniplayer** | **全站常驻；退出播放页可选小窗播放或纯音频，作品信息显示在条上** | C4（新增） |
| 新番时间表 | 真数据（Bangumi `/calendar`） | A2 |

## 4. 阶段划分（只划到 v1，不给绝对工期）

你说不要一次性规划到软件成熟，边用边迭代（F3、§3-5）。所以这里**不排周数、不排到 v5**，只划 v1 内部的大致阶段与**出口条件**——做到什么算这一步过了，由出口条件判断，不由日期判断。

| 阶段 | 目标 | 出口条件（过了才进下一阶段） |
| --- | --- | --- |
| **S1 骨架与还原** | Electron 壳 + 路由 + SQLite + 全站页面 1:1（走 seed） | 全站页面可点通、无 404 漏网；原型 CSS 在壳里表现一致 |
| **S2 内容与源** | Bangumi 刮削 + 规则导入（含 Kazumi 转换）+ 真实搜索详情 | 能搜到真实作品并显示真元数据；能导入一条社区规则并跑通搜索 |
| **S3 能真的看** | 播放链路 + 跨源拼集 + 失效切换 + miniplayer | **真实源完整播完一集**；杀进程重开回到上次秒数；退出后可小窗/纯音频继续 |
| **S4 能囤** | 下载队列 + 断点续传 + 文件夹识别 + 资源管理 | 整季下载完成并断点续传验证；扫描本地目录能识别出作品；删除有确认 |
| **S5 v1 收口** | 全站走查 + 自动备份 + 托盘 + 迁移演练 | 定稿 §8 四问全过；红线检查脚本 0 报警；备份与恢复演练通过 |

**S5 之后进入「用起来 → 补能力 → 再走查」的循环**：先把 v1 拿去真用（你自己 + 几个朋友），按实际痛点点下一个迭代要补的分区或能力（阅读器、音乐、游戏、弹幕…），不再预先排长表。

## 5. 可行性：我认为最可能卡住的三件事（请重点看）

### X-1 · 「界面全做」与「禁止假交互」的冲突（**已选 乙**）

- 定稿 §8 明确禁止：**假交互（点了没反应）**。
- 但 v1 只有动漫分区是真能力 → 游戏分区点「启动游戏」、音乐分区点「播放全部」、阅读器点章节，**点了都没反应**，这直接违反红线。
- **你已选 乙**：保留全部页面，所有未实现动作统一给**明确的「功能未开放」提示**（原型就是这么处理的：按钮已就位，点击给 toast 说明）。**代价是踩「禁止假交互」红线，已在定稿 §9 登记 v1 豁免**（`16` 任务）：未实现的「功能未开放」提示**不视为**假交互；且每一处「未开放」都须在定稿 §9 清单里登记，**不许出现第二处同类未登记项**。
- 丙（把阅读器/音乐也做进 v1）已排除：与 B1「不要求」相左。

### X-2 · 跨源自动拼集是最大技术不确定性

- 你要的是「跨源自动拼出一整季，每集可能来自不同站」（D3），这比 `07` 现在写的「按集列出候选 + 自动选最优源」更难：需要**集数对齐**（不同站的集数编号、缺集、OVA/SP 混排、番剧分季）与**逐集可用性探测**。
- Kazumi 只做到「搜索 + 选集 + 内部嗅探」，**没有跨源拼集**——这块没有现成经验可抄，需要我们自己定算法。
- 风险：拼错集（第 7 集拼到别的话数）比不拼更糟。建议 v1 先做「按集选源 + 失败回落」，把「整季自动拼」作为 S3 内的增强项，做成可开关。

### X-3 · 真实源的可持续性与新番数据

- A2 要「必须真能拉到新番数据」：元数据侧（Bangumi `/calendar`）没问题，但**播放侧**依赖源站规则，新番往往只有少数站有、且更新快、失效频繁。
- 缓解：规则版本化 + 社区导入 + 失效自动切换（D1）+ 健康度可见。但要有心理准备：**部分新番可能搜得到、播不了**，这是源生态决定，不是实现问题。

### X-4 · 视频嗅探是新增工作量

- `08` §6.3：Kazumi 靠内部嗅探拿直链。我方原方案（本地代理 + hls.js）只覆盖「规则直接给出 m3u8/直链」的站。要吃下 Kazumi 社区那批「只带到播放页」的规则，**必须补嗅探**，这是 `07` 里原本没有的一块。
